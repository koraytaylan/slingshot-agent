# Plan 0008 — Author Console and Diagnostics — 🚧 Integration pending

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** 🚧 Integration pending.
- **Goal:** put this agent where an operator already looks, assemble the four stores into the one answer somebody diagnosing an operation actually wants, and publish readiness into the author's own operations dashboard — with no front-end toolchain and no Adobe resource overlaid.
- **Root cause:** everything built so far is answerable only by a client that already knows what to ask, which is the wrong shape for the operator who has just installed this and for whoever is looking at an operation that went wrong. The second one has an identifier and a question whose answer is spread across four stores that only this repository knows how to read, and without a console the answer is "check the logs".
- **Approach:** register under Adobe's own tools extension point by adding rather than overlaying, with the package filter checked so nothing shadows an Adobe resource at the next upgrade; render server-side from Granite's own components with Java data sources and one hand-written client library, taking no package manager, bundler, or framework, because a second dependency graph would undo the compatibility argument the whole repository rests on; apply the routes' own permitted-group requirement and redaction corpus to every console resource and data source, hiding the navigation entry from a viewer who may not use it rather than showing them a refusal, and deciding authorization separately from the service-user read the data sources perform; assemble snapshot, ledger, attempts, lease, and artifacts into one operation view and follow a running one through the same event route the client uses rather than a second stream; surface generation, capacity, and the last sweep where an operator would otherwise never think to look; publish six separately-caused health checks into the operations dashboard rather than one aggregate, including the two that catch what only somebody else's instance can break — routes the servlet resolver's configuration never registered, and a declared query whose covering index this repository no longer has; correlate every log line by operation identifier under the same redaction rules; and prove all of it by asserting server-rendered markup and data-source responses over HTTP, because a browser driver is a large dependency for something a server response already determines.

- **Exceptions:**
  - **The console lives in the Sling-only bundle rather than the Adobe one.** Every task in this plan named `aem/src/main/java/rs/slingshot/agent/aem/console`, and the four screens, the paging shape, the authority and the two link types were written there first. They cannot stay there. The Adobe bundle's imported-package footprint is a committed four packages, and the console references the store, the route table, the contract, discovery, the registry and the authorization gate — none of which the Sling-only bundle exports, and exporting them would trade a closed publication boundary for a console that touches no Adobe API at all. The container analyser found it first, as eight packages imported at a start level nothing exports them for. The console now sits at `core/src/main/java/rs/slingshot/agent/console`, its tests run under `-pl core`, and the Adobe bundle is back to the one thing that genuinely needs an Adobe runtime. The per-task `Done when` commands naming `-pl aem` read `-pl core`.
  - **The six health checks are not registered as Felix `HealthCheck` services.** Task 3301 asks for each to appear in the author's own dashboard under its own name and tags. The health-check API is reachable only from the Adobe bundle, which registers no OSGi service in this build and has no test double available offline for one — the attempt to add `sling-mock` to that module in Plan 0006 failed against the locked cache and would fail here for the same reason, and six components with no unit coverage would breach the per-class coverage floor. What each check is called and which two tags it carries is declared on `AgentHealth.Check` and proved distinct; the checks themselves are complete and proved, including the two that catch what only somebody else's instance can break. The registration is a wiring task for whichever plan gives this bundle its first Adobe-side component.
  - **The interoperability scenarios named `rs.slingshot.agent.interop.<X>Scenario` sit in `rs.slingshot.agent.interop.tier`,** beside the eighty-odd that were already there. A scenario needs a tier to run against, and the package is where every tier scenario lives.
  - **`ConsoleDataSource` is a final class holding a screen rather than a base a screen extends.** The shape rules refuse a public class that is neither final, sealed, nor an interface, and a sealed base cannot be extended by a test double. Handing a screen to the gate is the stronger arrangement anyway: an inherited method can be overridden, and a screen that was given nothing but a chance to produce rows has nothing to override. The register gained one pattern for it — `protection-proxy` — whose signature the build now checks.
