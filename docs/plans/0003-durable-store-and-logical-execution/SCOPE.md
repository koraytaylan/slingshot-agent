# Plan 0003 — Durable Store and Logical Execution

> One logical operation, exactly one effect, across a job system that delivers at least once, a cluster that can move work between nodes, and a process that can stop between any two lines.

## Why this plan

The client's whole recovery story rests on one assumption about this side: that the agent treats the stable operation identifier derived from the local operation as an idempotency key. A request that left the client and never produced an answer is the interesting case, because the command may or may not be running here. The client is built to look the operation up rather than resubmit it, and to reconcile from what the agent says rather than from what it assumed — which is only sound if what the agent says is durable, monotone, and the same after a restart as before one.

Underneath, Sling's job system delivers physically at least once. A job can be retried, a cluster can move it to another node, and a node can stop holding one. So a duplicate physical record is not a defect to be prevented; it is the normal case, and the design has to make it harmless. One logical operation, an outbox that records physical attempts without multiplying them, and a fence that means at most one worker is executing at any instant — that is the arrangement, and every part of it has to survive the process ending between any two steps.

The repository is Oak, and Oak has exactly two primitives worth building on. Creating a node at a path either succeeds or fails because something is already there, atomically, across the cluster; and a property write can be made to fail rather than merge when somebody else changed the same property since the read. Claim by creation, update by compare-and-set, and nothing else. Everything durable in this plan is one of those two — including counting, which looks like a third and is not: Oak's atomic counter mixin consolidates its increments asynchronously on a clustered document store, so a decision taken on one is correct on a single instance and quietly wrong on the cluster a Cloud Service author actually is. Counts here are sharded properties advanced by compare-and-set, and every property about contention is proved on two nodes sharing one repository rather than on two sessions of one.

Nothing on the hot path issues a repository query. An operation is found at a path derived from its identifier, an event at a path derived from its sequence, an artifact at a path derived from its slot. That is not a performance micro-decision: a query needs an index, an index needs to be current, and "the index had not caught up yet" is an answer that is wrong rather than slow — which is exactly what an idempotency check must never be.

## In scope

- **0009 — Repository Layout, Generation, and Accounting.** One state tree with a path derived from every identifier, bucketed so no node grows wide enough for Oak to degrade; the durable event-store generation that starts at one, never repeats, and never decreases; the two conditional-write primitives everything else is built from, with a bounded retry that fails rather than merges; the durable key ring that gives Plan 0002's authority contract a cluster-safe home; and the one accounting authority every later admission goes through, bounded per caller as well as per generation so no client can spend the store on everybody's behalf — built here rather than beside its callers, because an authority that arrives after them is one several of them have already written their own version of.
- **0010 — Logical Operations, Outbox, and Fenced Execution.** The logical operation record claimed by creation at its own path; idempotency decided by the independently derived submission digest and, beside it, the target identity and environment revision that digest does not cover, so a resend converges and a different command — or the same command aimed elsewhere — under one identifier is a conflict rather than a silent overwrite; an outbox recording bounded physical attempts without multiplying the logical one; the Sling job consumer that maps a physical record to a logical operation and holds a submission out of the queue until every payload its manifest declared has arrived; and the execution lease with renewal, no takeover before expiry, and no second effect.
- **0011 — Ledger, Snapshots, Subscriptions, Artifacts, and the Terminal Commit.** An append-only ledger bounded per operation and per generation, admitting through the accounting authority rather than through a counter of its own; a materialised snapshot that agrees with the ledger by construction rather than by a job that keeps them in step; a subscription ledger with high-water marks and a bounded number of live subscriptions; replay from a cursor under the rule that a reconnection with no cursor exposes nothing already exposed and retracts nothing that was; an artifact store with a byte count and a digest written before the artifact is reachable and capacity reserved before the work that will fill it starts; and, last because it needs all of them, a terminal transition that writes the outcome, the result, the terminal event, and the snapshot in one commit or none, naming an artifact the store has already committed and writing none itself.
- **0012 — Retention, Recovery, and the Crash Proof.** Retention anchored where the client anchors it, with a declared minimum nothing may shorten and a request-start this side refuses to accept from beyond its own clock's declared allowance; a bounded, resumable, deterministic maintenance sweep that never collects bytes a worker is still about to name; recovery — at startup and on an interval, because an author may not restart for weeks — that classifies rather than executes, since it holds no session to execute under: an operation that never started is left for the client's own resend to start, one started past its execution budget is undetermined, and nothing is re-identified or resubmitted; explicit generation rotation with bounded prior retention; and a container scenario that kills the instance mid-flight and proves one effect on the other side of it.

## Out of scope

- Every route and every servlet. Plan 0004 owns the transport surface, and this plan's stores are reached through interfaces it will call.
- Every command. The execution framework here runs a handler; what a handler does is Plans 0005 through 0007.
- The protocol documents themselves, which Plan 0002 owns and this plan persists without redefining.
- Any user interface. Plan 0008 owns the console that reads these stores.

## Plan dependencies

Plan 0001 supplies the contract accessor, the service user and its access-control list, the two-bundle split that keeps all of this in `core`, and the interop harness this plan's crash proof runs on. Plan 0002 supplies every document persisted here, the identity types the paths are derived from, the submitted-command digest idempotency turns on, and the key-ring contract this plan gives a durable implementation.
