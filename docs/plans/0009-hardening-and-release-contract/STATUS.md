# Plan 0009 — Hardening and Release Contract — 🚧 Integration pending

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** 🚧 Integration pending.
- **Goal:** attack every guarantee the previous eight plans built, then produce a release whose every claim is either checked or explicitly not made.
- **Root cause:** this runs inside somebody else's author instance, with a service user, in the same process as their content and their configuration, which makes a defect here a defect in their environment rather than in a tool they run. And a release is a claim about bytes, source, behaviour, and supported environments, every part of which is wrong by default unless something proves it.
- **Approach:** write the privilege-escalation suite first because it is the one that says whether the whole architecture's central guarantee holds, and attack in every direction the design makes possible rather than the ones that seem likely; fuzz all four places bytes arrive from somewhere else, coverage-guided from a committed corpus with a pinned offline tool, against one property each — a valid value or a refusal naming a bound, never a partial value or an unbounded allocation; fuzz the canonical writer from the other direction, since the round trip is what the five-field identity rests on; prove the three state machines behind the one-effect argument by generated sequences against four invariants rather than by more examples; run chaos on two nodes wherever the property is about contention and inject at the boundaries a cluster actually has, with clocks getting their own suite because every lease is a comparison of two instants and a decision may be conservative and never wrong; snapshot the wire so a protocol change is a visible decision, prove storage compatibility by upgrading a populated instance rather than installing a fresh one, and bind the platform floor to the deployment matrix rather than to a second declaration; authenticate one exact reviewed advisory snapshot offline with no freshness claim, because a snapshot's author chooses its timestamp; make the archives deterministic and prove it by building twice, publish a components list because embedding nothing is a claim worth verifying, decide every prerequisite the central Maven repository enforces offline rather than discovering it from the portal after a release run has reached the network, publish one built set byte-identically to both distribution targets so an operator's file and an embedding project's coordinate can never diverge, and bind every deployment row to the evidence that actually ran against it so a row with none stays declared and unproved; pin every workflow action to a commit with least privilege, no persisted credentials, and one job holding attestation; and leave both real-author verification and publication as decisions a person makes explicitly rather than things a build does.

- **Exceptions:**

What runs on every build instead is the same seven targets over the same committed corpus plus a seeded run of mutations of it, which is the half that costs nothing and therefore never stops running. Every property the tasks name is asserted; what is absent is the longer search, and it is absent visibly rather than silently.
  - **The property-based generator is this repository's own rather than a new dependency.** Task 3504 asks for one to be added to the tooling dependency set. It cannot be: the cache is locked and no generator is in it. The four invariants are asked over seeded sequences from a generator written here, with a shrinker, with every counterexample recorded as a permanent case that runs without generation, and with each property shown to be capable of failing against a deliberately broken mechanism. Nothing in the task's own test list went unproved.
  - **The fuzz targets and the property models are test sources.** Every task in workstream 0035 named them under `development/src/main`. What runs against a real cluster is the scenario, and it runs where somebody has one. The interoperability tier itself has a pre-existing discrepancy this plan did not introduce and did not fix: a scenario expects a submission carrying only a command name to be refused as malformed and the public tier answers it as unauthorized, because the tier's authenticated user is not in the permitted group.
